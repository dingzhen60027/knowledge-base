# CodeGraph：给 AI 编码助手一张代码地图

## 问题：AI agent 看代码是靠"翻文件"

用过 Claude Code、Cursor 这类 AI 编码助手的人应该都有体会：当你问它一个跨文件、跨模块的问题时，它不会直接知道答案。

它会做一系列动作：

1. `grep` 搜索关键词
2. 打开搜索结果里的文件，逐行读
3. 看到 import 引用，又去打开另一个文件
4. 不断重复，直到拼出完整的上下文

这个过程极度依赖**工具调用**——一次问答可能触发几十次 `grep` 和 `Read` 操作。每个工具调用都要消耗 token、消耗时间、消耗钱。在大项目（比如 VS Code 这种上万文件）上，这个问题尤其突出：agent 花大量 token 在"找路"上，而不是真正理解代码。

## 解法：预索引的知识图谱

CodeGraph 的思路很直接——**与其让 AI agent 每次自己翻文件，不如提前把代码结构整理成一张图，agent 来了直接查图**。

这张图（知识图谱）包含的是代码中的**语义关系**：

- 哪个函数调用了哪个函数（调用图）
- 哪个类继承自哪个类（继承关系）
- 哪个模块导出了什么符号（符号索引）
- 哪个接口在哪里被实现（实现关系）

这些信息在代码编译/运行前就已经能确定，完全可以提前计算好，没必要让 agent 在运行时重新发现。

## 效果：更少工具调用，更便宜，更快

官方在 7 个真实开源项目（VS Code、Django、Tokio、OkHttp、Excalidraw、Gin、Alamofire）上做了对照测试，中位结果：

| 指标 | 提升幅度 |
|------|---------|
| 成本 | **便宜 16%** |
| Token 消耗 | **减少 47%** |
| 耗时 | **快 22%** |
| 工具调用 | **减少 58%** |

有意思的是文件数量越多效果越明显。在 VS Code（~1万文件）上，工具调用减少了 **81%**，token 消耗少了 **64%**。因为在超大项目中，agent 找路要花的精力最多，而一张完整的地图正好解决这个问题。

## 怎么做到的

CodeGraph 的工作流程是离线的：

1. `codegraph init -i` 扫描项目，构建知识图谱，存到 `.codegraph/` 目录
2. `codegraph install` 把它注册成 AI 助手的 MCP 工具
3. AI agent 遇到代码问题时，调用 `codegraph_explore` 查询图谱，直接拿到答案

这个过程不需要联网，索引是**纯本地**的，数据也不会离开你的机器。

> [!info] MCP（Model Context Protocol）是 AI 工具和 AI 模型之间的标准协议。简单理解：MCP 工具 ≈ AI agent 的"插件"，让 agent 能做更多事情。

## 适用场景

- **大型代码库**（几千到上万个文件）——效果最明显，找路成本高
- **不熟悉的老项目**——不需要人力先读一遍代码，agent 直接查图回答
- **架构评审 / 代码审查**——快速回答"这个改动会影响哪些模块"
- **CI 场景**——APR（自动 PR 审查）等自动化流水线中，省 token 就是省钱

## 对比：不用 CodeGraph 会怎样

没有预索引的情况下，AI agent 在代码库中探索是一个"盲目搜索"的过程：

```
用户提问 → grep 找关键词 → 读文件 A → 发现引用 B → 读文件 B 
→ 发现引用 C → 读文件 C → 拼凑理解 → 回答
```

有 CodeGraph 的情况：

```
用户提问 → codegraph_explore 查图 → 直接回答
```

前者的工具调用次数和执行时间随项目规模线性增长；后者基本恒定，因为它已经知道所有代码的位置。

## 局限性

- **需要初始化步骤**：新克隆的项目需要先跑 `codegraph init -i`
- **增量更新**：代码改动后需要重新索引（但社区版支持 git-aware 增量更新）
- **不是所有场景都需要**：小项目、单文件问答应答直接用 agent 翻文件可能更快

## 总结

CodeGraph 本质上是在做一个"空间换时间"的权衡——用磁盘空间存一份预计算的知识图谱，换取 AI agent 运行时更少的工具调用和更低的 token 消耗。

对于一个经常用 AI 编码助手处理复杂代码库的开发者来说，安装成本和收益之间的性价比是清晰的：一次初始化，换来每次问答更少的等待和更低的费用。
